## 五、本次抓到的缺陷

### 🔴 缺陷 1（阻塞级）：`pack.sh` 行尾校验在 Windows 上**误报**，导致打包永远失败

```
xx 以下文件仍含 CR，拒绝打包：
     backend/app/config.py
     backend/app/db.py
     ...（几乎全部文件）
```
- **实测反证**：用 Python 逐字节扫描 42 个脚本类文件 → **含 CRLF 的 0 个，纯 LF 的 42 个**
- **判定**：检测逻辑 `grep -l $'\r'` 在 Windows/Git Bash 环境下把 **CR 字节当作空模式**传给 grep → 空模式匹配一切 → **全量假阳性**
- **影响**：本次打包被拦，只能手动复刻 tar 规则绕过；换台 Windows 机器部署会**100% 卡死**
- ⚠️ **讽刺之处**：这个校验本是 9/17 为修 CRLF 缺陷而加的"防御"，如今它自己变成了阻塞点 —— **防御逻辑本身也需要被验证**
- **待修复**：改用 Python 或 `grep -c $'\r'` 的可靠写法，并在 pack.sh 里加「检测到失败时输出调试信息」而非静默列文件

### 🟡 缺陷 2：镜像版本被更换，引入环境差异

用户重装时选的镜像 ID 由 `lhbp-c6e7uu0g` 变为 **`lhbp-7wrz1nyu`**（非原版本），初始状态因此不同：

| 项 | 旧镜像 | 新镜像 |
|:---|:---|:---|
| caddy | 手动安装 | **预装且服务已在运行** |
| redis-server | 已装 | **未装** |
| sqlite3 | 已装 | **未装** |
| fail2ban | 已装 | 未装 |
| cron | 5 条 | 1 条 |

- **影响**：`deploy.sh` 幂等覆盖后仍然得到正确结果 ✅（说明脚本对新旧镜像都健壮）
- **结论**：若目标是"与原来完全一致的重建"，重装时应**显式选回原镜像**；本次意外变成了一次"**换镜像重建**"测试，结论是**通过**

### 🟡 缺陷 3：MCP 对 `.ssh` 路径硬拦截 → 公钥恢复必须人工

- 现象：含 `/root/.ssh`、`/home/ubuntu/.ssh` 的 TAT 命令**稳定 `AccessDeny`**；命令换成不含该路径的其他内容立刻通过
- **影响**：重装后「恢复 SSH 通道」这一步**无法由 AI 自动完成**，必须人工在 VNC 粘贴
- **缓解**：已把命令固化为 `drill-20260928/restore-pubkey.txt`（单行、可直接粘贴）
- 📌 这也解释了为何 TAT 可用仍需人工介入：**TAT 通了，但写公钥这条路被策略挡住**

### 🟡 缺陷 4：「重置密码」被误当成「重装系统」（操作层）

- 用户先后两次表示"已重置"，实机核查均为零变化（`who -b` 不变、站点目录仍在、`LatestOperation` 为空）
- **根因**：控制台里「重置密码」与「重装系统」入口相邻，前者**只改密码、不碰系统盘、不重启**
- **沉淀**：判定"是否真的重装/重启过"的可复用手法 = `describe_instances` 看 `LatestOperation` + TAT 里 `who -b` / `uptime` 的**连续性**

### 🟡 缺陷 5：`deploy.sh` 收尾未提示「立刻补跑首次备份」

- 全新系统上备份目录为空 → 首次执行 `alert.py` 必报一项异常：「备份目录里找不到任何 `app-*.db.gz`」
- 这是**正确告警**，但部署者可能误判为故障
- **待改进**：`deploy.sh` 收尾的三件事里增补第 4 项 —— 「立即执行 `bash backup.sh` 生成首个备份，再跑 `offsite-backup.py` 验证外发」

### 📌 附：AI 自身的一次失误（记录在案）

- 首次生成公钥恢复命令时，**手工重排 745 字符的 RSA 公钥，漏掉中段 `kC3J2Zt8cu/`**，产出了无效公钥命令并已发给用户 → 自查时发现并纠正
- **纠正做法（已固化为脚本 `gen_restore_cmd.py`）**：一律从**文件**生成，并做三重校验（三段式结构 / base64 解码长度 / `ssh-keygen -l` 指纹解析）
- 📌 **教训：长密钥、长哈希绝不允许手工复制重排**
